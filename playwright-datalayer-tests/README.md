# `playwright-datalayer-tests/` — Machine-Generated Playwright Tests

This folder holds **Playwright `.spec.js` test files**, one per analytics event in `specs/`. They are auto-generated by the pipeline and run against a live URL to validate that `window.dataLayer` actually contains the events your specs describe.

Don't edit these files by hand — they're regenerated on every spec change.

---

## What's in here

```
playwright-datalayer-tests/
├── add_to_cart.spec.js
├── login.spec.js
├── page_view.spec.js
├── purchase.spec.js
└── remove_from_cart.spec.js
```

One file per event. Each is fully **self-contained** — no shared helpers, no relative imports. You can lift any single file out and run it standalone.

### What's inside each file

A standard Playwright test file structured as:

- An inline `waitForDataLayerEvent()` polling helper
- An inline `getAllDataLayerEvents()` helper (for duplicate / no-duplicate assertions)
- One `test.describe('<event_name>', ...)` block
- A `test.beforeEach()` that navigates to `process.env.TEST_URL`, triggers the event, captures the dataLayer payload
- Multiple `test()` blocks, **one assertion per test** — event presence, event name, each parameter, business rules

This structure is enforced by the test generator's prompt. Every file in this folder follows the same shape, which is what makes the output predictable.

## Who writes it

| Workflow | When |
|---|---|
| [`Generate Playwright dataLayer Test`](../.github/workflows/README.md#7-generate-playwright-datalayer-test--generate-testsyml) | After every spec merge to main, chained off the artifact pipeline |
| Manual `workflow_dispatch` | On demand for a specific spec |

The agent that produces these files is [`agents/test-generator/`](../agents/test-generator/README.md).

---

## How tests get executed

The test generator only **produces** these files. It doesn't run them. Execution is handled by a separate workflow:

| Workflow | Triggers | Purpose |
|---|---|---|
| [`Validate dataLayer`](../.github/workflows/README.md#10-validate-datalayer--validate-datalayeryml) | Manual `workflow_dispatch`, or PR with `TEST_URL:` in body | Installs Playwright + Chromium, runs the tests against a live URL |

This split is intentional: tests get **generated** as part of the spec lifecycle (every merge), but **executed** only when an analyst decides to validate against a real environment. You don't want every spec change to spin up a browser.

## Running tests locally

To run any single test against a live URL:

```bash
# One-time setup
npm install
npx playwright install chromium

# Run a specific event's tests
TEST_URL=https://your-staging.example.com \
  npx playwright test playwright-datalayer-tests/add_to_cart.spec.js

# Run all of them
TEST_URL=https://your-staging.example.com \
  npx playwright test playwright-datalayer-tests/
```

The `TEST_URL` env var is required — every generated test reads it via `process.env.TEST_URL` to know where to navigate.

## Why you should not edit these files by hand

**1. They will be overwritten.** Any manual edit is blown away when the underlying spec changes and the workflow re-runs.

**2. They follow a strict structural contract.** The generator enforces one-assertion-per-test, inline helpers, specific polling patterns. Hand edits will diverge from that shape and confuse future regenerations.

**3. Bugs belong in the spec, not the test.** If a test assertion is wrong, the underlying spec is wrong. Fix the spec and let the test regenerate.

**The one legitimate exception:** if you want to add interaction setup that the generator can't infer (e.g. logging in a user before testing `add_to_cart`), the right path is to extend the test generator's prompt — not patch the file. See the test-generator README's notes on the [interaction-events limitation](../agents/test-generator/README.md#the-interaction-events-limitation).

---

## When the file might look out of sync

- **Mid-PR:** the test file updates only after a spec merges to main, not on the spec PR
- **After a spec is deleted:** the old test file stays in this folder until manually removed
- **Interaction-heavy events:** the generator produces test stubs that may need refinement before they actually pass against a live URL. The skeleton is valid; the trigger conditions may not be
