# login

Tracks when a user successfully authenticates into their account.

---

## Overview

This event fires immediately after a user completes a successful login. It captures the authentication method used (e.g., email/password, Google SSO, magic link) and the user's internal identifier. This data helps the business understand login success rates, preferred authentication methods, and supports user journey analysis across sessions.

---

## Trigger Rules

- ✅ The user has submitted valid credentials and the authentication API has returned a **success response**
- ✅ The event fires on the `/login` page (or wherever the login form is submitted)
- ✅ Fire only **after** successful authentication—not on form submission or button click
- ✅ Must use transport beaconing to ensure the event is captured even if the page immediately redirects after login
- ❌ Do NOT fire on failed login attempts
- ❌ Do NOT fire on session restoration (e.g., returning user already logged in via cookie)
- ❌ Do NOT fire on password reset or account creation flows

## Business Rules & Edge Cases

1. **PII Restriction (Critical):** The `user_id` must be a hashed value or internal database ID. Never pass cleartext emails, usernames, phone numbers, or any other personally identifiable information. Violation of this rule may breach privacy regulations (GDPR, CCPA).

2. **Transport Beaconing:** Because login often triggers an immediate redirect (to dashboard, originally requested page, etc.), configure GTM to use `navigator.sendBeacon()` or equivalent transport method to ensure the event fires before the page unloads.

3. **Authentication Method Values:** Use consistent, lowercase, snake_case values for `method`. Common values include:
   - `email_password`
   - `google_sso`
   - `facebook`
   - `apple`
   - `magic_link`
   - `saml`
   - `two_factor`

4. **Single-Page Application (SPA) Handling:** If login occurs via a modal or inline form without a page reload, ensure the dataLayer push happens in the authentication success callback, not on route change.

5. **Session Restoration:** Do not fire this event when a user returns to the site and is automatically logged in via a persistent session cookie. This event is strictly for active authentication actions.

6. **Selector Clarification Needed:** The spec notes that the login form selector is not specified. Work with the analytics team to confirm the exact DOM element or API endpoint that should trigger the GTM custom event.
