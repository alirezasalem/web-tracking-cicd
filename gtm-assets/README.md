# `gtm-assets/` — Machine-Generated GTM Container Exports

This folder holds **importable GTM container JSON files**, one per analytics event in `specs/`. They are auto-generated by the pipeline and ready to import directly into Google Tag Manager.

Don't edit these files by hand — they're regenerated on every spec change.

---

## What's in here

```
gtm-assets/
├── add_to_cart-gtm-export.json
├── login-gtm-export.json
├── page_view-gtm-export.json
├── purchase-gtm-export.json
└── remove_from_cart-gtm-export.json
```

One file per event. The filename is `<event_name>-gtm-export.json`. Each file is **self-contained** — it includes its own trigger, dataLayer variables, and GA4 event tag.

### What's inside each file

A GTM container-export JSON envelope containing:

- **1 custom-event trigger** matching `event: <event_name>`
- **N dataLayer variables** (one per key in the spec's `dataLayer` block)
- **1 GA4 event tag** wired up to the trigger with all variables as event parameters
- Standard GTM built-in variables (Page URL, Page Path, Referrer, Event)

The structure follows GTM's standard import format — open the file in GTM via **Admin → Import Container** and it works.

## Who writes it

| Workflow | When |
|---|---|
| [`Generate GTM Config`](../.github/workflows/README.md#8-generate-gtm-config--generate-gtmyml) | After every spec merge to main, chained off the artifact pipeline |
| Manual `workflow_dispatch` | On demand for a specific spec |

The agent that does the actual writing is [`agents/gtm-generator/`](../agents/gtm-generator/README.md). It uses **no AI** — pure deterministic JS transformation from YAML to JSON.

## How to use these files

The intended workflow is:

1. Open GTM → Admin → **Import Container**
2. Choose the relevant `<event>-gtm-export.json` file from this folder
3. Pick a target workspace (clean workspace recommended for first imports)
4. Choose **Merge** (not Overwrite) to preserve existing resources
5. Review the diff GTM shows you
6. Click **Confirm**

**One file = one GTM import.** Each file is independently importable. If you import multiple files into the same workspace, GTM remaps overlapping IDs automatically — but reviewing each diff individually is easier than untangling a multi-event merge.

For full GTM import instructions, see [`../agents/gtm-generator/README.md`](../agents/gtm-generator/README.md#importing-into-gtm).

## Why you should not edit these files by hand

**1. They will be overwritten.** Any manual edit gets blown away the next time the source spec changes and the GTM generator runs.

**2. The shape is rigid.** GTM expects a precise container-export format. A misplaced field or missing ID silently breaks the import.

**3. The IDs are coordinated.** Each file uses an internal ID scheme (trigger 101, tag 102, variables 110+). Editing these by hand risks collisions or broken references.

**If you need to change what's in these files**, the right path is to edit the source spec in [`specs/`](../specs/) and let the workflow regenerate the JSON.

---

## When the file might look out of sync

- **Mid-PR:** the GTM JSON updates only after a spec merges to main, not on the spec PR
- **After a spec is deleted:** the old GTM JSON stays in this folder. The pipeline doesn't currently clean up after deletions — manual removal needed
- **After changing `pipeline.config.yaml → gtm` settings:** existing files won't auto-regenerate. Manually re-trigger `Generate GTM Config` via `workflow_dispatch` to refresh them all
